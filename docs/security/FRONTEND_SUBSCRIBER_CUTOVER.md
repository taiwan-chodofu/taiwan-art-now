# Frontend subscriber cutover plan — review only, NOT deployed

## Verified current template callsites

Inspected the draft branch versions of `templates/index.html`, `templates/nearby.html`, and `templates/exhibition_detail_page.html`. All three implement local-first favorites/visited state using `localStorage` keys `taiwan_art_favs` and `taiwan_art_visited`, and send ref-based sync to `/api/subscribers/sync` using `taiwan_art_ref`. The home template also calls `/api/subscribers/status?ref=...` and `/api/subscribers/unsubscribe`, and Web Push `/api/push/subscribe` and `/api/push/sync-favs`. `/api/push/vapid-public-key` is public key discovery, not a private subscriber mutation.

`scripts/audit_frontend_subscriber_calls.py` inventories exact literal fetch callsites and fails the release gate while legacy calls remain. This is a limited static scan: dynamically constructed URLs, external scripts and other templates are NOT covered. It does not prove security. Run `python scripts/audit_frontend_subscriber_calls.py --report-only` for an inventory in CI, or without `--report-only` for a blocking check.

## Migration contract

1. **Do not discard local favorites/visited.** Continue using localStorage for anonymous browsing and offline/PWA behavior. Never automatically overwrite local favorites/visited with empty remote data on auth failure.
2. **Do not treat `taiwan_art_ref` as identity.** Ref values in localStorage are legacy migration hints only. Do not submit them to new private routes.
3. **After Meta-verified two-secret session establishment**, use `GET /api/private-subscribers/status` (no identity query) and `POST /api/private-subscribers/sync` with exactly `{favs, visited}`; server determines sender. Settings and unsubscribe likewise send no IDs.
4. **Reconciliation is unresolved.** Local and remote may contain different items. Decide and test per-item merge precedence, removals/tombstones, conflicts across devices, schema validation and offline replay before switching on automatic sync. Current draft API status does not return remote favorites/visited, so it cannot perform safe two-way reconciliation yet.
5. **Push is a separate identity domain.** A browser PushSubscription endpoint and its keys are not authorization by themselves. Design a verified endpoint possession and rotation protocol before replacing `/api/push/subscribe` and `/api/push/sync-favs`; preserve independent anonymous Push users.
6. **Legacy unlink/ref operations** must be redesigned around verified Meta sender, not a browser-provided ref. Unsubscribe must not remove another subscriber's ref.
7. **Cutover and rollback:** encrypt and verify owner-controlled backup, pause legacy writers, take final snapshot, atomically import into private PostgreSQL, verify counts/content without exposing subscriber data, migrate authenticated clients behind a controlled flag, keep public legacy endpoints closed to IDOR, and maintain a tested rollback strategy that does not silently lose writes. Remove GitHub-backed JSON and remediate public Git history only after safe backup and explicit owner approval.

## Release blockers

- Blueprint not registered; no real Meta-to-browser challenge completion or browser claim UI.
- Real PostgreSQL integration, disposable staging concurrency, and session authorization transaction semantics untested.
- Browser route ownership audit and frontend callsite audit still block release.
- Ref-link and Push ownership missing.
- Local/remote merge and offline conflict rules missing.
- Existing production subscriber JSON in public GitHub history requires separate privacy remediation.
- **No production schema, subscriber data, deployment, or branch merge changed by this plan.**

## Conservative reconciliation prototype (NOT enabled)

`subscriber_reconciliation.py` now provides a **pure, additive-only** local/remote merge for the two maps `favs` and `visited`. Keys found on either side are retained; identical keys with equal values are stable. A key with different values on two devices is a conflict and **blocks the entire merge** rather than silently overwriting either value. A metadata-only preview exposes counts, not private values. Thirteen synthetic tests cover union, conflicts, idempotent replay, preservation of remote/local records, invalid input, and no mutation of original snapshots. **This is not a complete conflict-resolution or deletion protocol**: absence cannot distinguish deliberate deletion from an out-of-date device, and false values or nested objects may carry semantics that need product review. Tombstones, per-item revisions, authoritative server versions, explicit user conflict choice, and a transaction-bound compare-and-swap are required before any automatic two-way sync. The existing `/api/private-subscribers/sync` currently replaces maps; it MUST NOT be exposed as a conflict-safe merge endpoint. No production data was accessed or modified.

## Revisioned tombstone state machine (draft only)

`versioned_subscriber_sync.py` introduces a separate pure state-machine prototype with server `revision` and per-item `{value, deleted, revision}` records for `favs` and `visited`. A deletion is an explicit tombstone; absence from an old device cannot delete or resurrect a record. A batch carries `base_revision` and is rejected with `StaleRevision` if it differs from current state. Every accepted nonempty batch increments the server revision once; a stale device must refetch and explicitly reconcile, never blindly retry. Fifteen synthetic tests cover stale replay, tombstones, invalid state and batch consistency. **This does not yet guarantee concurrency correctness**: production persistence must perform a database-transaction compare-and-swap on the revision under an appropriate lock, and return 409 on stale revisions. Legacy `localStorage` maps have no tombstones or revision metadata and need a reviewed one-time import protocol; they cannot simply be treated as authoritative deletes. Retention/compaction, size limits, payload schema and a recovery path for lost revisions also need decisions. Neither existing private sync endpoint nor the frontend uses this module. No live database schema was changed.

## PostgreSQL revision compare-and-swap adapter (draft; not executed)

`versioned_subscriber_store.py` provides a draft transactional store for a **server-verified sender only**. It acquires a per-sender transaction advisory lock (including the absent-row bootstrap), reads the JSONB state with `FOR UPDATE`, applies `versioned_subscriber_sync.apply_changes`, and writes only if the stored revision still matches the supplied `base_revision`. A missing row is inserted with `ON CONFLICT DO NOTHING RETURNING`; conflicts raise `StaleRevision` and roll back. The SQL schema in `docs/security/VERSIONED_SUBSCRIBER_SCHEMA_DRAFT.sql` is **review-only and has NOT been applied**. Seven synthetic tests cover update/insert races, stale revisions, rollbacks and no-op batches. **No live PostgreSQL concurrency test has run**; transaction semantics, FK prerequisites and real psycopg JSONB round trips must be verified on independently provisioned disposable staging before any route integration. Server session resolution must occur inside the trusted request path; do not accept a sender ID supplied by the browser. This adapter does not yet return HTTP 409 or merge legacy data and is not used by the current routes.

## Disposable PostgreSQL concurrency CI (added; pending verification)

The workflow now includes a separate `disposable-postgres-cas` job using an ephemeral PostgreSQL 17 GitHub Actions service on localhost with a synthetic-only database named `tan_ci_disposable`. `tests/test_disposable_postgres_cas.py` bootstraps synthetic tables and one synthetic subscriber, then launches eight concurrent independent psycopg connections with the same base revision and asserts exactly one accepted update and seven stale-revision rejections. The test refuses non-localhost or differently named targets and requires `TAN_CI_DISPOSABLE_POSTGRES=1`; it does not use Supabase credentials. The initial CI attempt failed because psycopg was not installed in the synthetic unit-test job; the workflow now installs the pinned driver. **CI results for the new integration job must be inspected before claiming success.** This test is not equivalent to the real production schema and does not authorize cutover.

## Isolated versioned HTTP v2 contract (draft, not registered)

`versioned_subscriber_api_routes.py` defines `GET /api/private-subscribers/v2/state` and `POST /api/private-subscribers/v2/changes`. The write payload is exactly `{base_revision, changes}`, without sender/ref/endpoint IDs. The route locks the cookie session row `FOR UPDATE` in the same connection/transaction as `versioned_subscriber_store.update_for_verified_sender`, and translates stale revisions to HTTP 409; missing/revoked sessions to 403, invalid payloads to 400, outages to 503. Both routes are intentionally NOT registered in `app.py`. Ten synthetic HTTP tests cover owner binding, status and conflict behavior. These routes are a draft and still require a real Meta claim flow, production schema review, data migration, frontend conflict UX, and staging end-to-end validation. The legacy API is not replaced and no deployment has occurred.

## Browser-side v2 sync coordinator (isolated; NOT loaded)

`static/js/draft_versioned_sync.js` is a standalone UMD module for a future authenticated browser flow. It reads `GET /api/private-subscribers/v2/state`, compares a caller-supplied local snapshot, and only sends `POST /api/private-subscribers/v2/changes` for **unambiguous additions absent on the server**. Remote-only items, differing values and tombstones that conflict with local items require review; they never cause an automatic overwrite. A 409 returns `stale_revision` without retry; a network loss after POST returns `unknown_commit` (the write might have succeeded), so clients must refetch before any retry. Unauthorized, offline and invalid-server responses do not change localStorage. The module does not itself read or mutate localStorage, does not transmit legacy ref/sender IDs, and is not imported by any existing template. Node's built-in test runner covers offline, conflicts, tombstones, remote-only items, no retry and no identity parameters. **This is deliberately conservative and not a complete two-way merge**: local deletions cannot be inferred from absence, remote-only values require explicit reconciliation, and current localStorage shape and schema migrations still need validation. Never enable automatically on production until authenticated browser claim, user-facing conflict resolution and server-side staging integration are complete.

## Verified legacy localStorage shape and read-only adapter

Re-inspected actual draft branch templates `index.html`, `nearby.html`, and `exhibition_detail_page.html`. Both collections are **objects keyed by normalized exhibition key**, not arrays. Favorites use metadata objects with `title`, `museum`, `dates`, `url`; visited records are ISO timestamps created with `new Date().toISOString()`. All three templates remove entries with `delete map[key]`, so absence cannot prove an intentional deletion versus an older device or missing record. `static/js/draft_legacy_snapshot.js` provides a **read-only** parser for the two actual localStorage keys, validating object shape and expected value types and returning `invalid_local` on corruption instead of replacing it with empty data. No browser storage writes, no legacy ref identity, and no automatic conversion into tombstones. Twelve synthetic Node tests added. The adapter is NOT loaded by the templates. Future migration must account for legacy records that differ from the observed shapes and must never silently discard them.
